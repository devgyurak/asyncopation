# AGENTS.md

Instructions for every coding agent working in this repository (Claude Code, Codex, Pi).
Claude Code loads this file through `CLAUDE.md`.

## Project
Asyncopation (`django-asyncopation`, import `asyncopation`) gives the Django ORM a truly
asynchronous execution path: Django's compiler still generates SQL (sync, no I/O), and we
execute it on native async drivers (psycopg3, asyncmy) with contextvars-based connection
ownership. Python 3.12+, Django 6.1 (pinned minor), ASGI only. Status: pre-alpha.

Read before non-trivial work: `docs/design/plan.md` (plan and roadmap), `docs/architecture.md`
(layers and invariants), `docs/adr/` (decisions).

## Non-negotiables
1. **No thread hops in `src/`.** No `sync_to_async`/`async_to_sync`, threads, executors, or
   Django's sync connection/transaction machinery. SQL generation stays sync; I/O is async.
2. **Layering** is enforced (`make guard`). Drivers are the only importers of psycopg/asyncmy.
3. **Tests:** Given/When/Then markers and **zero control flow** (`for/while/if/try/match/
   comprehensions/ternaries`) in test modules. Logic goes to `tests/support/`.
4. **Differential correctness:** read APIs must match the sync ORM (values, types, order,
   exceptions) on PostgreSQL, MySQL and MariaDB.
5. **Django internals** used or ported are recorded in `docs/django-api-ledger.toml`.
6. **English** for comments, docstrings, docs, commits. Selected human docs have `-XX`
   translations (`README-KO.md`) that must stay in sync (`docs/i18n.toml`).
7. **Fix code, not guards.** There are no suppression comments for project guards.
8. **Generated agent files** (`.claude/agents|rules|skills`, `.codex/agents`, `.pi/agents`) are
   never edited directly - edit `.agents/` and run `make agents-sync`.
9. **Docs move with the code.** Every change updates the documents that describe it in the same
   change (README, architecture, ADRs, ledger, plan checklist, skills/rules, translations) - see
   the `docs-sync` rule for the full "if you change X, update Y" table.

## Workflow
Every change follows the `feature-loop` skill: frame -> research -> design check -> red tests
-> implement -> refactor -> `review-change` (parallel sub-agent review) -> perf (hot paths) ->
close (plan checklist, docs, ledger, translations). Details: `docs/workflow.md`.

Definition of done: `make check-all` green, review has no open BLOCKER/MAJOR, every document
listed by the `docs-sync` rule updated, plan checklist ticked, the GitHub issue closed by the PR.

Tracking: every roadmap item is a GitHub issue in a `Phase N` milestone, labelled by type
(`feature`, `perf`, `test`, `ci`, `documentation`, ...), layer (`area:*`) and backend
(`backend:*`). `needs-decision` marks issues waiting on a human/ADR. Pick work from the current
phase milestone and reference the issue in the PR (`Closes #N`).

Commits and branches: one prefix per change - `ADD:` `FIX:` `REF:` `DEL:` `DOCS:` `UPT:` - with an
English summary and a body explaining why (`ADD: alist() on aobjects for PostgreSQL`). Work
branches `<prefix>/<kebab-summary>` are cut from `develop` and PR'd into `develop`; `main` only
receives release merges from `develop`. Details: the `commit` skill. Do not commit or push unless
asked.

Branch protection (GitHub rulesets): `develop` changes only via PR with the code owner's
(@devgyurak) approval - the maintainer may bypass-merge; `main` accepts no direct pushes from
anyone, only PRs from `develop`. Releases are `vX.Y.Z` git tags on `main` (tag push -> release CI,
issue #26). Agents never push to `main`/`develop`, approve, merge or tag.
