## [Unreleased]

### Added
- `pytest-timeout` (dev dependency): every test has a 120 s timeout so a hang fails the test instead of slowing the run.
- Phase 0: agentic workflow (Claude Code / Codex / Pi), guards, differential/e2e/benchmark harness.
- `asyncopation.drivers` (internal, experimental; not a stable API): `AsyncDriver` / `AsyncDbConnection` protocols and the frozen `Capabilities`, `ExecResult` and `PoolStats` value types (#2).
- PostgreSQL driver on psycopg3 (`PostgresDriver`) (#2):
  - Django-compatible connection setup (adapters template, `client_encoding`, isolation level, `TimeZone`, `assume_role`, `OPTIONS["server_side_binding"]`) and Django's error mapping.
  - Pool from `OPTIONS["pool"]`: `OPTIONS["pool"]` accepts `None`, `True`, `False` or any mapping of `psycopg_pool` `AsyncConnectionPool` keyword arguments (`min_size`, `max_size`, `timeout`, `max_lifetime`, ...). `None`, `True` and `False` all mean "use the defaults" (provisional `min_size=1`, `max_size=10` until the #8 benchmark): the async side always pools, a deliberate divergence from Django, where `pool=False` means no pool, and the driver ignores `CONN_MAX_AGE`. Other types, unknown keys, `close_returns` unless it is exactly `False`, and the keys `name`, `configure`, `kwargs`, `conninfo` and `open` (the driver passes those itself) are rejected with `ImproperlyConfigured`; `OPTIONS["cursor_factory"]` (not a pool key) is still rejected by name. `min_size` and `max_size` must be integers (`max_size` may be `None`), `max_waiting` an integer >= 0, `num_workers` an integer >= 1, and `timeout`, `max_lifetime`, `max_idle` and `reconnect_timeout` an `int` or `float`; a `bool` is never accepted for any of them. `connection_class` is allowed only as a subclass of `psycopg.AsyncConnection` - the key must be absent otherwise, and `None` is rejected like any other bad value; any other callable value is rejected too (sync hooks do not fit an async pool). An explicit `check=None` switches the `CONN_HEALTH_CHECKS` check off. A size the user gives is never corrected (a missing `max_size` defaults to `max(10, min_size)`), so `min_size > max_size` is not fixed up: `psycopg_pool`'s builtin `ValueError` is raised from `open()` before any connection is made (an explicit exception to ADR-0003 Decision 4, which covers database errors; this is a configuration error). `CONN_HEALTH_CHECKS` enables the pool's `check_connection`.
  - `open()` connects directly first (bad credentials or `assume_role` fail immediately, no pool is left behind) and builds `Capabilities`, available only while the driver is open.
  - Cancellation safety: a cancelled statement is cancelled and rolled back; inside a transaction or with an open stream the connection is discarded. Streams still open at release are closed; a `CLOSE` that fails when a stream ends inside a transaction raises (as Django does), mapped to `django.db` per ADR-0003 D4 (Django leaves it unmapped) (not when another error is already propagating; the failed cursor is forgotten only when the error is `InvalidCursorName` or the cursor is not held, otherwise it stays tracked and `reset()` closes it after the rollback; in autocommit it is retried at release); a failed `COMMIT` restores autocommit.
  - A released connection wrapper, and its stale stream iterators, raise `InterfaceError`.
- PostgreSQL driver: hstore and citext type handlers (#43, ADR-0003 Decision 2). With `django.contrib.postgres` in `INSTALLED_APPS` (read by `configure()`), `PostgresDriver.open()` reads the type OIDs once on its first connection (Django's `pg_type` query, every schema) and every connection registers the handlers on its own adapters without I/O, so `HStoreField` reads `dict`, `ArrayField(HStoreField())` `list[dict]` and `citext[]` `list[str]`, as with the sync ORM. The OIDs are not refreshed until the next `close()` / `open()`. The harness gains the PostgreSQL-only app `harness.pgcatalog`.
- Compile-only PostgreSQL `DatabaseWrapper` and the synchronous `compile_scope` (internal, experimental; not a stable API) (#3, ADR-0008): Django generates SQL for an alias without ever connecting (`asyncopation.compile`, `asyncopation._django.connections` is the only module that touches `django.db.connections`), `compose_sql` renders `SearchHeadline` options without a driver for the exact built-in types, and the guards A102 / A104 enforce the boundary (psycopg names Django re-exports, adapter helpers, `BaseWrapper` construction).
- Lifecycle, driver registry and server-info probe (#5, ADR-0004): add `asyncopation` to `INSTALLED_APPS` (`AppConfig.ready()` runs `configure()`, which builds the per-alias PostgreSQL configuration without I/O and can be called again until a driver is open or opening); `await asyncopation.setup()` / `await asyncopation.close(timeout=10)`; `asyncopation.connection.asgi.LifespanApp` opens the pools at lifespan startup and closes them at shutdown; using a database before `setup()` (the future query path) opens its pool once, lazily, with a logged warning. The process-global registry keys drivers by `(alias, loop)` and server info by alias (read-only `PoolStats`); the PostgreSQL server version is taken from the driver's capabilities once per alias and injected into the compile-only wrapper. MySQL/MariaDB raise `ImproperlyConfigured` at the first open until #7, and one alias that cannot be prepared (bad settings, missing driver library) never breaks `ready()`. `setup()` without arguments opens only aliases with a supported engine; an open fails closed with `ImproperlyConfigured` when `DATABASES` changed after `configure()` (the test runner's `NAME` rename: call `asyncopation.configure()` once the test databases exist). `close(timeout)` also bounds the wait for an open in progress (it is cancelled at the deadline), and `LifespanApp(app)` consumes the `lifespan` scope without passing it to the wrapped app (to combine it with other startup/shutdown work, call `setup()` / `close()` from your own lifespan handler). Pool size defaults are decided in #8.
- `aq(qs).alist()` on PostgreSQL (#6, ADR-0002, ADR-0006): `asyncopation.aq` wraps a QuerySet or Manager (`AsyncQuerySet`, applying `FETCH_RAISE`); chaining is proxied and re-wrapped, `await aq(qs).alist()` compiles with Django (`compile_scope`), runs the statement on the current executor and builds the same instances, dicts, tuples and named tuples as the sync ORM (`values()`, `values_list()`, `flat`, `named`, `select_related`, `only`/`defer`, `extra(select=...)`, composite primary keys), and fills the QuerySet result cache. A synchronous evaluator (`list()`, `len()`, `get()`, `count()`, `iterator()`, a slice with a step, ...) raises the new `asyncopation.SyncEvaluationError`; an `a*` method that is not implemented yet (coroutines and the `aiterator` async generator alike) and `raw()` raise `NotImplementedError` and never fall through to Django's `sync_to_async` version; `aq()` wraps a clone of the QuerySet you pass, so `alist()` fills the wrapper's cache and never yours (also for `|`, `&`, `^`, `union()`, `intersection()` and `difference()` with an empty operand, where Django returns the operand itself: the result is cloned; a user-defined chaining method must return a new QuerySet, and a combination or user-defined method that returns a QuerySet whose result cache is already filled shares that cache, as Django's returns the evaluated QuerySet; wrappers nested inside an argument (`Prefetch(queryset=aq(...))`, a list, a `Q`) are not unwrapped and are unsupported; keep the wrapper on the left of `|`, `&` and `^`, because `QuerySet | aq(...)` runs Django's operator and returns a plain QuerySet that does not get `FETCH_RAISE` from `aq()`; a QuerySet whose cache is already filled (a prefetched related manager, a QuerySet evaluated synchronously) keeps that cache's instances in their original fetch mode, which is not `FETCH_RAISE`; a Manager's own fresh QuerySet is used directly; one whose result cache is already filled is wrapped as it is), `aq()` of a Manager and `all()` of its wrapper, like `aq(tag.books.all())`, keep a many-to-many related manager's pending sticky filter (`aq(tag.books).filter(tags__name=x)` and `.all().filter(...)` match the sync ORM), compiling works on a copy of the Query so overlapping `alist()` calls on one wrapper stay correct, and the database router is asked once per evaluation; a QuerySet that cannot match (`.none()`, `pk__in=[]`) runs no statement but still opens the alias's pool; `prefetch_related` evaluation is not implemented (Phase 4). `aget`, `afirst`, `acount`, `aexists`, `async for` and the `aobjects` descriptor see the next entry; MySQL/MariaDB in #6 PR C and #7.
- Read API on PostgreSQL (#6, PR #67, ADR-0006, ADR-0007): `aget`, `afirst`, `acount`, `aexists` and `async for` on `aq()`, following Django 6.1's `get` / `first` / `count` / `exists` (`MAX_GET_RESULTS`, the `DoesNotExist` / `MultipleObjectsReturned` messages, unordered `first()` ordered by `pk`, the result-cache shortcut); `asyncopation.AsyncObjects` (`aobjects = AsyncObjects()` on a model, `AsyncObjects.attach(Model)` for third-party models) returns `aq()` of the default manager's QuerySet and is not a Django `Manager`. Internally the sans-I/O runner (`engine.runner`: `Compile` / `Execute` / `Convert` requests, `run_core`; the row conversion of an aggregation runs outside `compile_scope`, like the materializer) drives the cores of `Query.get_count`, `Query.has_results` and `Query.get_aggregation`, ported without their I/O in `_django/aggregation.py`. The harness models declare `aobjects`; `bench-micro` runs the `asyncopation.*` cases (it opens the pools first). When a core's cleanup raises while a run is cancelled or failed, the original exception (the `CancelledError`) is kept and the cleanup error is attached to it as a note. The clone `aget` and a querying `afirst` build is `FETCH_RAISE` even when the wrapper shares a QuerySet whose cache is filled in a user fetch mode; instances read from that cache keep their mode. `aobjects` does not refuse a swapped-out model (Django's manager descriptor does); attach it to the model in use.
- Compile-only wrapper for MySQL and MariaDB (#6, PR #68, ADR-0008 Decision 5; internal, experimental): `asyncopation.compile.mysql.MySQLCompileWrapper` generates SQL like Django's MySQL wrapper without importing `MySQLdb` (composed from Django's `mysql.features`, `mysql.operations`, `mysql.client`, `mysql.creation` and the `DatabaseWrapper` attributes ported from `mysql/base.py`); the server data Django reads with a query comes from a frozen `MySQLServerInfo`. The SQL/params identity sweep and a behavioural drift test against the real wrapper run on MySQL 8.4 and MariaDB 11.8. Guard A101 now bans importing `django.db.backends.mysql.base` / `.introspection` (and the gis MySQL ones) in `src`, because they import `MySQLdb`; the `DatabaseWrapper` members that are not ported are listed in `compile/mysql.py` and pinned by a source-level drift test that needs no mysqlclient (`tests/unit/django_drift/test_mysql_source_drift.py`); a MySQL `UPDATE` filtered through a join needs a connection while compiling and raises `CompileOnlyConnectionError` (a pinned limit; MariaDB and PostgreSQL compile it). The asyncmy driver, the probe and the engine registration (so `alist` on MySQL/MariaDB) are #7. The source drift test also covers members declared in class-level `if` / `try`, rejects `**`-built dict keys and pins the `MySQLServerInfo` field order to the `row[n]` order of Django's server query; the two CI drift steps (`django-drift` in the canary job, `integration-drift` in the integration job) have fixed ids in `ci.yml`, and `tests/unit/django_drift/test_pin_marker.py` finds them by id and compares each whole step except its `name` (so `run`, `env`, `if`, `continue-on-error`, `working-directory`, `shell`, `with`, ... must be exactly as expected), the job keys that can skip or neuter the step (`if`, `defaults`, `continue-on-error`, `needs`, `strategy.fail-fast`, `strategy.matrix.include` / `exclude`, `PYTEST_ADDOPTS` in the job `env`), a workflow-level `defaults` or `env.PYTEST_ADDOPTS`, and requires the canary's drift step to directly follow the Django main install step, itself compared whole except `name` (no shell parsing; the accepted gaps of this deny-list are in the `tests/support/pin_marker.py` docstring), so a command that only mentions `--no-sync`, `-m "not django_pin"` or `tests/unit/compile` in another segment, overrides `ASYNCOPATION_REQUIRE_MYSQLDB` or makes the step conditional fails the test. The `MySQLServerInfo` field order is load-bearing for the #7 probe (`MySQLServerInfo(*row)`) and the drift test asserts it.
- `asgiref>=3.13` is now a declared runtime dependency (#49, ADR-0008): `src` does not import asgiref, but `compile_scope` depends on the behaviour of `asgiref.local.Local(thread_critical=True)` (Django itself only requires 3.9.1; older versions were not verified). The drift suite pins that behaviour on `Local` itself and requires the installed version to equal the ledger's new `[[dependency]]` row.
- Executors and connection ownership (#5, ADR-0001): `asyncopation.ConcurrentQueryError` (a `RuntimeError`) is raised when a connection pinned to one task is used from another task, re-entrantly while a statement or stream is in flight, or after its block exited. Internally (`asyncopation.connection.executor`, not a stable API yet) a `BorrowedExecutor` borrows a pooled connection per statement and a `PinnedExecutor` keeps one connection per task; a statement cancelled inside a transaction marks it broken (later statements raise Django's `TransactionManagementError`, the connection is discarded), and `close(timeout)` waits for open pins and streams. There is no query API yet; when `async_atomic` arrives (#19), concurrent work (`gather`, `TaskGroup`) must run outside the transaction.
- `asyncopation.testing`: `RecordingDriver` (an `AsyncDriver` with queued results and a statement log, for unit tests; its connections raise `InterfaceError` after the borrow ends; a statement cancelled inside a transaction discards the connection - `RecordingConnection.discarded`, `RecordingDriver.discarded` - and `rollback()` on it is a no-op, as the driver contract requires) and `NoQueuedResult`, `RecordingConnection`, `Statement`, with `Capabilities` and `ExecResult` re-exported (#2).
- Query observers (#4, PR #74, ADR-0005): `with asyncopation.observe(fn, params=False):` calls the synchronous `fn(event)` for every call the current task tree makes to a connection (statements, streams, BEGIN/COMMIT/ROLLBACK and savepoints), with a `query_started` event right before the driver call and a `query_finished` event when it returns, fails or is cancelled (a stream: when it closes). `asyncopation.connection.QueryEvent` carries `name`, `alias`, `kind` (`query` / `transaction`), `sql` (descriptive text such as `SAVEPOINT s1` for transaction control), `params`, `many`, `rowcount` (rows returned by `fetch_all`, `ExecResult.rowcount` for `execute` / `execute_many`, the rows read by a stream, `None` for transaction control and failed calls), `error`, `queue_time` (wait for a pooled connection, 0 on a pinned one), `query_time` and `total_time` in seconds. A call that never gets a connection (a pool timeout) emits nothing. `params` is `None` unless the observer opted in (`params=True`) or `settings.DEBUG` is true. An observer that raises is logged on `asyncopation.connection` and never fails the query (a `BaseException` such as a cancellation propagates once the other observers got the event; raised by a `query_started` observer, it stops the call before the driver and `query_finished` still reports it; an observer's exception never marks a pinned transaction broken, and on a call that already failed it is attached to the original exception as a note); a coroutine function is rejected with `TypeError`, and an observer that returns an awaitable is logged (it is never awaited); the time `query_started` observers take is in neither `queue_time` nor `query_time`. `observe()` is single-use; leaving the block removes its registration even when it exits out of order or in another Context (an async generator closed by another task), and a task started inside the block reports to it only until the block exits. Observers run inline on the event loop for every query: they must not block. Process-wide observers (a startup-time call, like `configure()`): `asyncopation.connection.add_observer(fn, *, params=False)` / `remove_observer(fn)`. Subscribers are snapshotted when a call starts, so a stream closed later or from another task reports to the same observers. With nobody observing, the subscriber snapshot (`hooks.active()`) is two empty-tuple checks and the executors pass the driver call through unwrapped (`make bench-micro` gains the `hooks.*` executor cases on a `RecordingDriver`).

### Fixed
- Guard `testlint` (T1xx-T3xx) skipped every `test_*.py` under any folder named `support` (such as `tests/unit/support`); only the `tests/support/` helper package is exempt now; the search for the `# given` comment block of a test no longer treats a marker trailing the `def` line as part of the function (#6, PR #67).
- The shared compile-only wrapper (PostgreSQL and MySQL/MariaDB) is rebuilt when `USE_TZ` or `TIME_ZONE` change (#6, PR #68, ADR-0008 Decision 5): it used to keep the `timezone` / `timezone_name` it derived first, so SQL generated after a settings change (for example `override_settings`) adapted aware values in the old zone. A driver session that is already open keeps the zone it was opened with until `close()` and a new `configure()`.
