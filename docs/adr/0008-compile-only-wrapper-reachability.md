## Context
Plan §4.4 assumes SQL can be generated by calling `compiler.as_sql()` on a compiler bound to a
compile-only `DatabaseWrapper`. Django 6.1 does not keep that binding everywhere (verified with the
installed source):

- `SQLAggregateCompiler.as_sql` calls `self.query.inner_query.get_compiler(self.using, ...)`
  without the connection; `Query.get_compiler` replaces `connection` with `connections[using]`
  whenever `using` is set. A compiler created with `connection=wrapper` has `using=None`, so
  `AggregateQuery(...).get_compiler(connection=wrapper).as_sql()` raises
  `ValueError: Need either using or connection` - the path of `acount()` on sliced, distinct or
  aggregated querysets.
- `SQLUpdateCompiler.pre_sql_setup` runs `execute_sql(MULTI)` inside `as_sql` for MySQL multi-table
  updates and related updates: compiling an UPDATE is not I/O-free.
- Django reads `connections[...]` directly while building and evaluating querysets
  (`build_filter`, `QuerySet.get`, `bulk_create`, ...), outside any compiler we control.
- Building Django's own MySQL wrapper imports `django/db/backends/mysql/base.py`, which imports
  `MySQLdb`: mysqlclient would become a runtime dependency (today it is only in the `mysql-sync`
  dev group).
- Guard A102 forbids `django.db.connections` in `src/`.

## Options
### A - Install the compile-only wrapper as `connections[alias]` (spike: scoped, per async context)
Django's `ConnectionHandler` is thread-local in sync code and per async context inside a running
loop (see Spike results). The wrapper is swapped in only for the duration of one synchronous
compile call, so a permanent install on the loop thread is not needed (and would be wrong).
+ every direct `connections[...]` read and every `using`-based re-resolution inside the scope
reaches the wrapper.
- needs a reviewed, narrowly scoped exception to A102 (only in `asyncopation._django.connections`, see Decision 6);
sync ORM calls made from the same async context between scopes still see Django's own wrapper (they
already raise `SynchronousOnlyOperation` on the loop).

### B - Compiler subclasses returned by the wrapper's `ops.compiler()`
+ no global state. - every re-resolution point must be overridden, ledgered and drift-tested;
direct `connections[...]` reads outside compilers (`build_filter`, `get`) remain unsolved.

### C - Pre-warm Django's own wrappers with probed server info
+ reuses Django's wrappers unchanged. - per-thread wrappers must all be warmed; `pre_sql_setup` I/O
is still sync; requires mysqlclient for MySQL.

### Sub-decision - MySQL without mysqlclient
Build the MySQL compile-only wrapper from `mysql.features` / `operations` / `compiler` plus ported
`DatabaseWrapper` attributes (`operators`, `pattern_ops`, `data_types`, server-data properties),
or accept mysqlclient as a runtime dependency.

## Decision
**A, in its scoped form (A-scoped)**, with the MySQL compile-only wrapper composed without
mysqlclient. Evidence: "Spike results" below.

A-scoped, concretely:
1. `asyncopation.compile` exposes a synchronous context manager
   `compile_scope(alias, wrapper, *, autocommit)`. It remembers the current context's wrapper for
   `alias`, sets `connections[alias] = wrapper`, and restores the previous value (or deletes the
   entry when there was none) in `finally`; scopes nest as a stack (`get_compiler` inside
   `as_sql`). *Amended 2026-11-24 (#3, PR #45): the sentence "restores the previous value ... in `finally`" has one exception: a scope exited from another Context inside a running loop (below).* Nothing inside a scope may `await`, so no other task can observe the swap, and a
   cancellation cannot land inside it. It is entered per synchronous prepare phase, never for the
   lifetime of a loop thread or task. *Amended 2026-11-24 (#3, PR #45): added.* A scope must be exited in the `contextvars` Context that
   entered it: inside a running loop, exiting from another Context (a generator handed to
   another task) would overwrite that Context's own swap and autocommit, so it is detected, the
   entry is left untouched and `ScopeContextError` is raised (an exception from the body wins,
   except a `GeneratorExit`: the generator closed from another Context); without a running loop
   (plain threads) the previous entry is restored.
2. **Contract: every Django call that reads `connections[...]` must run inside a scope.** That is
   the whole prepare phase of each core step (building the compiler with
   `get_compiler(using=alias)`, `as_sql`, and ported helpers such as the `bulk_create` option
   checks), not only `as_sql`. Our ports never call Django methods that read `connections` outside
   a scope (see the orchestrate rows below: those methods are ported, not called). Materialization
   (`results_iter` / converters) uses the connection the compiler was built with and needs no
   scope; the sweep could not confirm this without rows, so #3 verifies it with the differential
   suite's "zero sync connections" assertion.
3. The wrapper's `autocommit` state is a scope argument, held in a `ContextVar` that the scope
   sets at entry and restores on exit; it is not an attribute of the wrapper, because a single
   wrapper per alias is shared across tasks *and threads*. *Amended 2026-11-24 (#3, PR #45): autocommit is held in a `ContextVar` instead of an attribute of the wrapper, after a four-thread experiment showed an instance attribute is read across threads.* `compile` does not import
   `connection` / `transaction`; the caller (engine) passes `not pinned`. The wrapper overrides
   `get_autocommit` to return the value; the only compile-time reader is `compiler.py:861`
   (`select_for_update`). `connect` / `ensure_connection` / `_cursor` / `cursor` / `chunked_cursor`
   / `create_cursor` / `get_new_connection` raise. *Amended 2026-11-24 (#3, PR #45): `cursor`,
   `chunked_cursor`, `create_cursor` and `get_new_connection` are added to the raising set.* Server
   info is injected before first use (`pg_version`; `mysql_server_data`). Concurrent tasks in
   different transaction modes (`asyncio.gather`) and concurrent loop threads do not interfere.
   *Amended 2026-11-24 (#3, PR #45): the `compose_sql` override and its contract, the rest of this
   item.* One further Django code path that asks for a live connection while generating SQL
   (besides `get_autocommit` for `select_for_update`, above) is `ops.compose_sql` (reached by
   `contrib.postgres` `SearchHeadline` options through `mogrify` -> `connection.cursor()`); the
   compile-only operations override it with a plain-Python renderer: no driver (psycopg stays
   confined to `drivers/`) and no dependence on server settings. It supports exactly the types that
   caller passes: the *exact* built-in types `str`, `int`, `float`, `bool`, `None` and finite
   `Decimal` (a leading space for finite negative numbers, signed zeros included), byte for byte
   like Django on a live connection (checked in the integration tests against psycopg's compiled
   `binary` build and its pure-Python implementation: `make test-compose-python`, run in CI; a
   source-built `c` implementation was not checked). Every other type raises `TypeError` at build
   time: dates, `bytes`, arrays, ranges and the like, non-finite `Decimal` (the two implementations
   render the NaN variants differently: the `binary` one `-NaN` as ` -NaN` and
   `NaN123` as `NaN123`, the pure-Python one every such value as `'NaN'::numeric`; `±Infinity`,
   plain NaN and positive sNaN are rendered alike by both, `-sNaN` differs like `-NaN`; all are
   rejected together to keep a single rule), and every *subclass* (`IntEnum`, `TextChoices`,
   Django `Choices`, ...), because the two psycopg implementations disagree about subclasses (they
   call `__int__`, `encode`, `__contains__`, `__str__`, ... of the subclass or not) and an
   overridden `__str__` would put arbitrary text into the SQL. `params` must be exactly a `list`
   or `tuple`. For the exact types the rendering is the live one; the errors are not always: a NUL
   character in a string is a `ValueError` (live: psycopg's `DataError`), a lone surrogate in
   `sql` or a value a `UnicodeEncodeError` like live (a string with both reports the surrogate
   first, as the `binary` implementation does; the pure-Python one reports the NUL, so its
   exception class differs from ours), wrong counts and unsupported placeholders are `ValueError`
   (live: `ProgrammingError`; `TypeError` for `%(name)s` with a list; `%b` / `%t` render live).
   Placeholder shapes and the parameter count are checked before any value is rendered.
4. I/O-bearing Django steps are ported as ADR-0007 cores, not reached through the wrapper:
   `Query.get_aggregation` (compile outer query, `Execute`, convert), `QuerySet.exists` /
   `has_results`, and `SQLUpdateCompiler.pre_sql_setup` + `execute_sql` related updates (Phase 5).
   *Amended 2026-11-25 (#6, PR #67): `get_aggregation` is ported in `_django/aggregation.py`, split at
   the I/O seam (`prepare_aggregation` / `finish_aggregation`), and driven by `engine/cores.py`; the
   runner wraps every synchronous stretch of a core in `compile_scope`, except the `Convert`
   request that carries the row through the converters (user `from_db_value` code), which runs
   outside any scope (ADR-0007 Decision 1).*
5. MySQL / MariaDB: compose the compile-only wrapper from `mysql.features`, `mysql.operations`,
   `mysql.compiler` and ported `DatabaseWrapper` attributes; mysqlclient is not a runtime
   dependency of Asyncopation. With the stock `ENGINE = django.db.backends.mysql` Django itself
   loads mysqlclient at startup (it loads the `default` backend while defining models,
   `Options.contribute_to_class`), so users keep mysqlclient for Django's sync paths (`migrate`,
   admin, sync views, `Model.objects`); Asyncopation paths use the composed wrapper and asyncmy,
   with one settings module. **An Asyncopation-specific `ENGINE`** (two settings modules, to drop
   mysqlclient from production images) **is not adopted**: it makes `connections["default"]`
   unusable for everything that needs a real connection and the cost outweighs the benefit; if it
   is ever reconsidered it gets its own ADR, and it is not decided in #6. A drift test compares the
   ported attributes with `django/db/backends/mysql/base.py`.
   *Amended 2026-11-25 (#6, PR #68, first round): the MySQL compile-only wrapper `compile.mysql.MySQLCompileWrapper` is `CompileOnlyMixin` + Django's backend-neutral `BaseDatabaseWrapper` (exported as `BaseWrapper` by `_django.mysql`, which never imports `MySQLdb`), composed with `mysql.features.DatabaseFeatures` and `mysql.operations.DatabaseOperations` (`mysql.compiler` is loaded by name through `ops.compiler()`). `BaseDatabaseWrapper.__init__` instantiates `client_class`, `creation_class`, `introspection_class` and `ops_class`, so it also uses `mysql.client.DatabaseClient` and `mysql.creation.DatabaseCreation` (neither imports MySQLdb in Django 6.1.3) and the backend-neutral `BaseDatabaseIntrospection` (`mysql.introspection` imports MySQLdb); `SchemaEditorClass` stays `None`. The `DatabaseWrapper` attributes Django defines in `mysql/base.py` (`vendor`, `_data_types`, `data_types`, `_limited_data_types`, `operators`, `pattern_esc`, `pattern_ops`, `isolation_levels`, `get_database_version`, `display_name`, `data_type_check_constraints`, `mysql_server_info`, `mysql_version`, `mysql_is_mariadb`, `sql_mode`, `server_version_re`) are ported into `compile/mysql.py` (ledger `ported = true`, header `# Ported from django/db/backends/mysql/base.py`); `mysql_server_data` is injected into the wrapper's `__dict__` from the frozen `MySQLServerInfo` before first use (once per wrapper: `wrapper_for` builds a fresh wrapper when the info changes). `connection.Database` is a small shim exposing only `Binary = bytes` (`BinaryField.get_db_prep_value` reads `connection.Database.Binary`; `MySQLdb.Binary` is `bytes`); `Database` is not ported from Django. The ported `server_version_re` is a plain `re.compile` (`django.utils.regex_helper` is not public API). The drift test compares the ported attributes, including the `cached_property` kind, with Django's class and runs the real wrapper's cached properties against the composed wrapper for the same injected server data; the SQL/params identity sweep runs on MySQL 8.4 and MariaDB 11.8. No new `_django` boundary exception; the asyncmy driver, the server-data probe and the engine registration remain #7.* *Amended 2026-11-26 (#6, PR #68, second review round):* (1) the time zone split: `wrapper_for` rebuilds the wrapper when `(USE_TZ, TIME_ZONE)` changes, on **both** backends (for PostgreSQL this changes behaviour: until now a wrapper kept the `timezone` / `timezone_name` it first derived), so the SQL generated by the wrapper (adapting aware values, `timezone_name`) follows the current settings; a driver session that is **already open** keeps the time zone it was opened with (the driver reads `use_tz` / `time_zone` once, in `Engine.prepare`, at `configure()`), so a settings change after `configure()` affects compilation but not the session time zone until `close()` and a new `configure()` (`configure()` refuses to run while a driver is open); (2) the cost is one `timezone_key()` call (two settings reads) per `wrapper_for` call: measured with `timeit` at about 0.4 us of the 0.75 us a `wrapper_for` call takes, against about 62 us (p50) for a scoped `as_sql()` in `make bench-micro` (`asyncopation.as_sql_scoped`), under 1 % (machine-dependent figures), so it is kept uncached: caching it per `setting_changed` signal would add a hook that is a test-only mechanism in Django, for a saving that is below the noise of the benchmark; (3) the members of Django's `DatabaseWrapper` that are **not** ported are listed explicitly in the header of `compile/mysql.py` (`SchemaEditorClass`, `validation_class`, `get_connection_params`, `get_new_connection`, `init_connection_state`, `create_cursor`, `_rollback`, `_set_autocommit`, `disable_constraint_checking`, `enable_constraint_checking`, `check_constraints`, `is_usable`; `Database` is a shim, the `*_class` attributes name Django's classes) and pinned by `tests/unit/django_drift/test_mysql_source_drift.py`, which reads Django's `mysql/base.py` as source (no mysqlclient). What it pins is: the set of class members (a new Django member, or one that disappeared, fails; a member assigned through a target the test does not understand fails loudly); the `ast.dump` of the ported methods (decorators included) and of the ported class attributes; `mysql_version` apart from the message of its error (the `if` test and the exception type are compared, the message is not); the keys of the dict `mysql_server_data` returns and which of its values are coerced with `bool(...)`, against the dict `apply_server_info` injects; and the `server_version_re` pattern. It does not pin the body of the server query itself (the live drift test on MySQL and MariaDB does, through behaviour), nor the bodies of members it does not list; (4) guard A101 bans importing `django.db.backends.mysql.base` and `.introspection` (and the gis MySQL ones) in `src`: both import `MySQLdb`; only bans were added, `_django/postgresql.py` still imports `postgresql.base` (psycopg is a dependency); (5) the `MySQLServerInfo` flags are coerced with `bool()` like Django does with the row, and the #7 probe must pass `VERSION()` as Django's query gets it, not the handshake version (a MariaDB handshake reports `5.5.5-10.11.6-MariaDB`, which Django's pattern parses as 5.5.5); (6) known limit, pinned by `test_a_mysql_update_filtered_through_a_join_needs_a_connection_while_compiling` in `tests/integration/test_compile_scope_differential.py`: on MySQL, `update_can_self_select` is false, so compiling an `UPDATE` filtered through a join runs the pre-select inside `as_sql`, which raises `CompileOnlyConnectionError` in the compile-only wrapper; MariaDB and PostgreSQL compile it without a connection; #6 offers no workaround (it would need its own decision, because the wrapper decision rejected real-connection wrappers); (7) the ported `mysql_version` error message is an f-string instead of `%r` formatting (same text).* *Amended 2026-11-26 (#6, PR #68, third review round):* (1) the ported `cached_property` is `functools.cached_property`, which Django main also uses, not `django.utils.functional.cached_property` (deprecated there, and not in the ledger's `[public]` list); this is a deliberate difference from Django's source, noted in the `reason` of the ledger row and the port header, and the drift tests treat both classes as the same descriptor kind; (2) guard A101 also bans `django.utils.module_loading` (`import_string` imports by dotted name and would bypass the import guards): `import M`, `from M import n` and `from P import M` (`from django.utils import module_loading`) are all reported. The `from P import M` form is now checked for every module in `BANNED_MODULES` (`_banned_submodule_name`; `django.db.transaction` is left to A102) and, as before, for the MySQL backend bans in `BANNED_BACKEND_MODULES` (`_banned_backend_module`); `from django.db.backends.mysql import *` is not reported and is no risk, because that package's `__init__` imports nothing banned; (3) consequences of the time zone split: a `wrapper_for` rebuild replaces `_WRAPPERS[alias]`, so a holder of the old wrapper keeps the old time zone, which is acceptable because `compile_scope` is handed the wrapper per call and nothing stores it; only bans were added, no boundary exception. *Amended 2026-11-26 (#6, PR #68, fourth review round):* the field order of `MySQLServerInfo` is now load-bearing: it is the column order of Django's `mysql_server_data` query (`row[0..5]`), so the #7 probe builds it positionally as `MySQLServerInfo(*row)` from that exact `SELECT`; reordering or inserting a field breaks positional construction, only the source drift test catches it (it asserts that Django's `row[n]` indexes are exactly `0..n-1`, in the order of the fields), and a mid-class insert needs this ADR amended. In the list of what the drift test pins (second round, item (3)) this adds: the field order, members declared in class-level `if` / `try` / `with` / loops / `match` (a member assigned through a target the test does not understand still fails loudly), and a `**`-built or computed dict key fails loudly. Separately, the two CI steps that run the MySQL wrapper drift suite have fixed ids in `ci.yml` (`django-drift` in the canary job, `integration-drift` in the integration job); the test tooling `pin_marker` finds each by id (exactly one, else it raises) and compares the whole step except its `name` (`run`, `env` and any other key such as `if` or `continue-on-error`), the job keys that can skip or neuter it (`if`, `defaults`, `continue-on-error`, `needs`, `strategy.fail-fast`, `strategy.matrix.include` / `exclude`) and a workflow-level `defaults` with the expected values, with no shell parsing, and requires the canary's drift step to follow the Django main install step, so a changed, extended, conditional or env-overridden step fails `test_pin_marker.py` and must be changed on purpose together with the expected mapping (this tooling is not covered by the drift test).
6. **A102 exception scope.** The exception covers one module, `asyncopation._django.connections`
   (ADR-0007), and within it only these operations: `connections.__setitem__` /
   `connections.__delitem__`, and the peek at the previous value through the private
   `connections._connections` (which avoids creating a real wrapper per task context just to
   remember it). *Amended 2026-11-24 (#3, PR #45): the two operations are reachable only through the single context manager `swapped`; the peek is not exposed.* *Amended 2026-11-25 (#5, PR #52): a fourth operation, a read of `connections.settings` (Django's configured `DATABASES`, defaults applied), reachable only through `configured_databases()`, which returns `_snapshot(connections.settings)` - a copy of the dict/list structure that shares the leaf values (`copy.deepcopy` fails in `ready()` on an `ssl.SSLContext` or a lock-holding object in `OPTIONS`); `connection/lifecycle.py` may import that one name.* Still forbidden in that module, as everywhere in `src/`: `.cursor()`,
   `ensure_connection`, `connect`, `django.db.transaction`, and any other use of a sync
   connection. `compile.scope` calls the module, through the single context manager
   `swapped(alias, wrapper)` that the module exposes (it yields nothing, so the previous wrapper
   is never handed out by any name the guard lets other code use); the guard lets only
   `compile/scope.py` import it, and also rejects dynamic imports (`importlib`, `builtins`,
   `__import__`). This narrows the issue's "`compile` module"
   wording to the Django boundary module and to these operations. The guard implementation is
   done in #3, not in this ADR.

   *Amended 2026-11-24 (#3, PR #45): the `swapped` form, the dynamic-import rejection, the `BaseWrapper` construction rules and the threat model below.*

   **Threat model of the guards (A101-A104).** They stop the code a contributor can write by
   accident: ordinary imports, attribute access, `getattr` with a constant name, and every route
   through Django or `asyncopation` *public* names (re-exports such as
   `django.db.models.base.connections`, `ConnectionHandler`, `psycopg_any`, `Database`,
   `BaseWrapper` aliases). They do not stop deliberate evasion: introspection and dunder walks
   (`__bases__`, `__mro__`, `__subclasses__`, `__loader__`, `__spec__`, `__dict__` / `vars()` of a
   module), `inspect`, `sys.modules`, strings assembled at run time, calling a function through a
   variable (`e = eval`), `gc`, `zipimport`. Those are known limits (listed in the `archlint`
   docstring, which has the full list; star imports are ruff F403) that architecture review
   covers, as are `BaseWrapper` handed on through `getattr(<asyncopation module>, "BaseWrapper")`,
   a call argument, `return` / `yield` or a lambda body inside `compile/` / `_django/`, an
   `asyncopation` module object held in a variable (access through it, `m = asyncopation;
   m._django.connections`, is not caught anywhere; inside `_django/` neither is
   `x = getattr(asyncopation, "_django")`, outside it that is A102; a name an
   import binds to the `_django` package itself, `from asyncopation import _django` or
   `import asyncopation._django as d`, is rejected, A102), and a class built with `type(...)`. The
   guard itself requires a class based on `BaseWrapper` to list `CompileOnlyMixin` before it and
   rejects calling `BaseWrapper(...)`, and a unit test checks the MRO of every Asyncopation
   subclass (of any Django backend wrapper) at run time (*Amended 2026-11-24 (#3, PR #45): the
   scope of that test*). Also known: psycopg objects that an
   `asyncopation.drivers` module re-exports under a public name
   (`from asyncopation.drivers.postgresql import sql`): ADR-0003 forbids that as a convention
   that review enforces, not the guards.
7. **Amendments applied with this acceptance:** AGENTS.md non-negotiable 2, `architecture.md`
   invariant 2 and `.agents/rules/architecture.md` / `async-correctness.md` gain the
   `compile_scope` exception (the synchronous swap in `_django.connections`; no `await` inside it);
   ADR-0004's "never in a contextvar" is qualified: the swap uses asgiref's contextvar-backed
   storage only transiently and carries no state across an `await`. *Amended 2026-11-24 (#3, PR #45): the `autocommit` `ContextVar` of Decision 3 is of the same kind: set and restored inside the synchronous scope, never read across an `await`, so ADR-0004's rule is qualified in the same way.*

## Spike results
Method. **The sweep installed the compile-only wrapper permanently** as `connections["default"]` so that every reachable read is recorded (a superset of what a scope covers; which of them a scope must enclose is the contract in Decision item 2). One-off scripts, not committed; the same check is owned from now on by the "zero sync
connections" assertion of the differential tests, #3). Django 6.1.3, PostgreSQL 17, MySQL 8.4,
MariaDB 11.8. Compile-only wrappers raised on `connect` / `ensure_connection` / `_cursor` and had
server info injected. Instrumented: `ConnectionHandler.__getitem__`, `Query.get_compiler`,
`SQLCompiler.__init__`, `as_sql` / `pre_sql_setup` / `execute_sql`, and the wrapper's connect

### Is `connections` thread-scoped? (hypothesis check - partly refuted)
- `ConnectionHandler.thread_critical = True`, but asgiref's thread-critical `Local` is
  **thread-local only in sync code**. Inside a running event loop it is backed by a contextvar
  (`asgiref/local.py`, `_ThreadCriticalLocal._get_storage`): the storage is per async call stack
  (copy-on-write; visible to awaited code and tasks created afterwards, not to siblings or the
  parent), still never visible to other threads.
- uvicorn probe (ASGI app on the loop thread): loop task, `asyncio.gather` children share one
  wrapper; `sync_to_async(thread_sensitive=True)` threads, `sync_to_async(thread_sensitive=False)`
  / `asyncio.to_thread` threads each have their own; a swap on the loop thread is invisible to them.
- pytest-asyncio (session loop) runs on the same main thread as pytest-django's DB setup, but a
  coroutine sees a **different** wrapper object than the sync fixture (`connections["default"]` in the
  loop is not the setup object); the sync oracle called through `sync_to_async` uses a third one.
  A scoped swap on the loop thread coexisted with sync oracle and core async calls; a swap in a child
  task was invisible to the parent and siblings. Teardown showed the usual "database is being
  accessed by other users" when a test left an in-loop real connection open (not related to the swap).
- Consequence: the "install it as the loop thread's `connections[alias]`" wording of option A is
  wrong; installation is per async context. A permanent install would (a) not reach other tasks
  and (b) shadow the real wrapper for sync-oracle code run in the same context. The scoped swap
  (decision item 1) avoids both. Its cost is not free: each swap and restore on asgiref's `Local` runs `get_running_loop`, copies the alias dict and allocates a storage object; a `bench-micro` case measures it (#3).

### MySQL without mysqlclient
- Composed wrapper (`mysql.features` + `mysql.operations` + `mysql.compiler` + ported attributes
  `_data_types`, `operators`, `pattern_esc`, `pattern_ops`, `isolation_levels`, `data_types`,
  `display_name`, `data_type_check_constraints`, `mysql_server_data` / `_info` / `_version` /
  `_is_mariadb`, `sql_mode`, `get_database_version`) never imported `MySQLdb` (asserted after each
  run). Importing `mysql.features`, `operations` and `compiler` does not import it; `mysql.base` and
  `mysql.introspection` do.
- SQL and params identical, compared with Django's own wrapper (server data injected into both):
  770 statements per backend (150 Hypothesis QuerySets x 5 evaluators plus 20 named reads / writes /
  `select_for_update` / JSON / regex / date lookups), **0 mismatches** on MySQL 8.4 and MariaDB 11.8;
  187 `features` / `ops` / wrapper attributes equal (only object identity and set ordering differ).
  Caveat: the real-wrapper side used PyMySQL installed as `MySQLdb` because mysqlclient's native
  libraries are not installed here; SQL generation does not depend on the client library.
- Finding that changes the sub-decision: Django loads the `default` backend while defining models, so
  with a stock `ENGINE` mysqlclient is required by Django whatever Asyncopation does. Without
  mysqlclient only works when `ENGINE` points at a module providing the compile-only wrapper
  (verified: `django.setup()` and the whole sweep ran with such an engine and no `MySQLdb`).
- PostgreSQL has no such split: `django.db.backends.postgresql.*` imports psycopg at import time, so
  `_django.postgresql` pulls psycopg in through Django (drivers remain the only direct importers).

### Deviations from the working hypothesis
1. `connections` is per async context inside a loop, not per loop thread (above).
2. `select_for_update` compilation connects (`get_autocommit`); not in the ADR's original list.
3. `pre_sql_setup` I/O is not MySQL-only: PostgreSQL / MariaDB hit it for multi-table inheritance. *Amended 2026-11-26 (#6, PR #68, second review round, item (6)): on MySQL an `UPDATE` filtered through a join raises `CompileOnlyConnectionError` in the compile-only wrapper (known limit, pinned by `test_a_mysql_update_filtered_through_a_join_needs_a_connection_while_compiling` in `tests/integration/test_compile_scope_differential.py`: on MySQL, `update_can_self_select` is false, so compiling an `UPDATE` filtered through a join runs the pre-select inside `as_sql`; MariaDB and PostgreSQL compile it without a connection; #6 offers no workaround, and one would need its own decision, because the wrapper decision rejected real-connection wrappers).*
4. Dropping mysqlclient from a project is only reachable through an Asyncopation `ENGINE`, not by the wrapper alone; that option is not adopted (Decision 5).

## Consequences
Unblocks Phase 1 `acount` / aggregate paths and the write compilers. Follow-ups: #3 adds the A102
exception for `asyncopation._django.connections` (operations listed in Decision 6, which run
through `swapped`; *Amended 2026-11-24 (#3, PR #45): the parenthesis*),
`compile_scope`, server-info injection and the "zero sync connections" assertion; #6 ports
`get_aggregation` / `has_results` and the MySQL composed wrapper with its drift test; Phase 5 ports
`pre_sql_setup` as a core. ADR-0002 and ADR-0004 refer to this ADR for how compilers reach the
wrapper and whether Django's own wrappers receive server info (they do not).

*Amended 2026-11-26 (#6, PR #68, second review round): for both backends the shared compile-only wrapper of an alias is rebuilt when `(USE_TZ, TIME_ZONE)` changes (a behaviour change for PostgreSQL too: until now the first derived time zone was kept), and a driver session that is already open keeps the zone it was opened with until `close()` and a new `configure()`.*

On MySQL / MariaDB with the stock `ENGINE`, Django still requires mysqlclient at startup, so
users run two connection pools (Django's sync one and Asyncopation's asyncmy pool); documentation
for that is tracked in the Phase 6 issue "Docs: MySQL setup notes".
