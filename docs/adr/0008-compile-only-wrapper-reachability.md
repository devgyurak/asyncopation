# ADR-0008: Compile-only wrapper - construction and reachability from Django code

- Status: Accepted
- Date: 2026-11-24
- Deciders: maintainer (@devgyurak) - accepted 2026-11-24 after the Phase 1 spike (#29)
- Architect review: raised by the architect review of ADR-0002/0004 (2026-11-24); spike results added 2026-11-24 and re-reviewed (approve with changes, incorporated)

## Context
Plan §4.4 assumes SQL can be generated by calling `compiler.as_sql()` on a compiler bound to a
compile-only `DatabaseWrapper`. Django 6.1 does not keep that binding everywhere (verified with the
installed source):

- `SQLAggregateCompiler.as_sql` calls `self.query.inner_query.get_compiler(self.using, ...)`
  without the connection; `Query.get_compiler` replaces `connection` with `connections[using]`
  whenever `using` is set. A compiler created with `connection=wrapper` has `using=None`, so
  `AggregateQuery(...).get_compiler(connection=wrapper).as_sql()` raises
  `ValueError: Need either using or connection` - the path of `acount()` on sliced, distinct or
  aggregated querysets.
- `SQLUpdateCompiler.pre_sql_setup` runs `execute_sql(MULTI)` inside `as_sql` for MySQL multi-table
  updates and related updates: compiling an UPDATE is not I/O-free.
- Django reads `connections[...]` directly while building and evaluating querysets
  (`build_filter`, `QuerySet.get`, `bulk_create`, ...), outside any compiler we control.
- Building Django's own MySQL wrapper imports `django/db/backends/mysql/base.py`, which imports
  `MySQLdb`: mysqlclient would become a runtime dependency (today it is only in the `mysql-sync`
  dev group).
- Guard A102 forbids `django.db.connections` in `src/`.

## Options
### A - Install the compile-only wrapper as `connections[alias]` (spike: scoped, per async context)
Django's `ConnectionHandler` is thread-local in sync code and per async context inside a running
loop (see Spike results). The wrapper is swapped in only for the duration of one synchronous
compile call, so a permanent install on the loop thread is not needed (and would be wrong).
+ every direct `connections[...]` read and every `using`-based re-resolution inside the scope
reaches the wrapper.
- needs a reviewed, narrowly scoped exception to A102 (only in `asyncopation._django.connections`, see Decision 6);
sync ORM calls made from the same async context between scopes still see Django's own wrapper (they
already raise `SynchronousOnlyOperation` on the loop).

### B - Compiler subclasses returned by the wrapper's `ops.compiler()`
+ no global state. - every re-resolution point must be overridden, ledgered and drift-tested;
direct `connections[...]` reads outside compilers (`build_filter`, `get`) remain unsolved.

### C - Pre-warm Django's own wrappers with probed server info
+ reuses Django's wrappers unchanged. - per-thread wrappers must all be warmed; `pre_sql_setup` I/O
is still sync; requires mysqlclient for MySQL.

### Sub-decision - MySQL without mysqlclient
Build the MySQL compile-only wrapper from `mysql.features` / `operations` / `compiler` plus ported
`DatabaseWrapper` attributes (`operators`, `pattern_ops`, `data_types`, server-data properties),
or accept mysqlclient as a runtime dependency.

## Decision
**A, in its scoped form (A-scoped)**, with the MySQL compile-only wrapper composed without
mysqlclient. Evidence: "Spike results" below.

A-scoped, concretely:
1. `asyncopation.compile` exposes a synchronous context manager
   `compile_scope(alias, wrapper, *, autocommit)`. It remembers the current context's wrapper for
   `alias`, sets `connections[alias] = wrapper`, and restores the previous value (or deletes the
   entry when there was none) in `finally`; scopes nest as a stack (`get_compiler` inside
   `as_sql`). Nothing inside a scope may `await`, so no other task can observe the swap, and a
   cancellation cannot land inside it. It is entered per synchronous prepare phase, never for the
   lifetime of a loop thread or task. A scope must be exited in the `contextvars` Context that
   entered it: inside a running loop, exiting from another Context (a generator handed to
   another task) would overwrite that Context's own swap and autocommit, so it is detected, the
   entry is left untouched and `ScopeContextError` is raised (an exception from the body wins,
   except a `GeneratorExit`: the generator closed from another Context); without a running loop
   (plain threads) the previous entry is restored.
2. **Contract: every Django call that reads `connections[...]` must run inside a scope.** That is
   the whole prepare phase of each core step (building the compiler with
   `get_compiler(using=alias)`, `as_sql`, and ported helpers such as the `bulk_create` option
   checks), not only `as_sql`. Our ports never call Django methods that read `connections` outside
   a scope (see the orchestrate rows below: those methods are ported, not called). Materialization
   (`results_iter` / converters) uses the connection the compiler was built with and needs no
   scope; the sweep could not confirm this without rows, so #3 verifies it with the differential
   suite's "zero sync connections" assertion.
3. The wrapper's `autocommit` state is a scope argument, held in a `ContextVar` that the scope
   sets at entry and restores on exit; it is not an attribute of the wrapper, because a single
   wrapper per alias is shared across tasks *and threads* (amended in #3 after a four-thread
   experiment showed an instance attribute is read across threads). `compile` does not import
   `connection` / `transaction`; the caller (engine) passes `not pinned`. The wrapper overrides
   `get_autocommit` to return the value; the only compile-time reader is `compiler.py:861`
   (`select_for_update`). `connect` / `ensure_connection` / `_cursor` / `cursor` / `chunked_cursor`
   / `create_cursor` / `get_new_connection` raise. Server info is injected before first use
   (`pg_version`; `mysql_server_data`). Concurrent tasks in different transaction modes
   (`asyncio.gather`) and concurrent loop threads do not interfere. The one Django code path found
   that asks for a live connection while generating SQL, `ops.compose_sql` (reached by
   `contrib.postgres` `SearchHeadline` options through `mogrify` -> `connection.cursor()`), is
   overridden by the compile-only operations with a plain-Python renderer: no driver (psycopg stays
   confined to `drivers/`) and no dependence on server settings. It supports exactly the types that
   caller passes: the *exact* built-in types `str`, `int`, `float`, `bool`, `None` and finite
   `Decimal`, byte for byte like Django on a live connection (checked in the integration tests
   against both the C and the pure-Python psycopg implementation). Every other type raises
   `TypeError` at build time: non-finite `Decimal`, dates, `bytes`, arrays, ranges and the like,
   and every *subclass* (`IntEnum`, `TextChoices`, Django `Choices`, ...), because the two psycopg
   implementations disagree about subclasses (they call `__int__`, `encode`, `__contains__`,
   `__str__`, ... of the subclass or not) and an overridden `__str__` would put arbitrary text into
   the SQL. `params` must be exactly a `list` or `tuple`. For the exact types the rendering is
   the live one; the errors are not always: a NUL character in a string is a `ValueError` (live:
   psycopg's `DataError`), a lone surrogate in `sql` or a value a `UnicodeEncodeError` like live
   (a string with both reports the surrogate first, as the C implementation does; the pure-Python
   one reports the NUL, so its exception class differs from ours), wrong counts and unsupported
   placeholders are `ValueError` (live: `ProgrammingError`, and `%b` / `%t` render live).
   Placeholder shapes and the parameter count are checked before any value is rendered.
4. I/O-bearing Django steps are ported as ADR-0007 cores, not reached through the wrapper:
   `Query.get_aggregation` (compile outer query, `Execute`, convert), `QuerySet.exists` /
   `has_results`, and `SQLUpdateCompiler.pre_sql_setup` + `execute_sql` related updates (Phase 5).
5. MySQL / MariaDB: compose the compile-only wrapper from `mysql.features`, `mysql.operations`,
   `mysql.compiler` and ported `DatabaseWrapper` attributes; mysqlclient is not a runtime
   dependency of Asyncopation. With the stock `ENGINE = django.db.backends.mysql` Django itself
   loads mysqlclient at startup (it loads the `default` backend while defining models,
   `Options.contribute_to_class`), so users keep mysqlclient for Django's sync paths (`migrate`,
   admin, sync views, `Model.objects`); Asyncopation paths use the composed wrapper and asyncmy,
   with one settings module. **An Asyncopation-specific `ENGINE`** (two settings modules, to drop
   mysqlclient from production images) **is not adopted**: it makes `connections["default"]`
   unusable for everything that needs a real connection and the cost outweighs the benefit; if it
   is ever reconsidered it gets its own ADR, and it is not decided in #6. A drift test compares the
   ported attributes with `django/db/backends/mysql/base.py`.
6. **A102 exception scope.** The exception covers one module, `asyncopation._django.connections`
   (ADR-0007), and within it only these operations: `connections.__setitem__` /
   `connections.__delitem__`, and the peek at the previous value through the private
   `connections._connections` (which avoids creating a real wrapper per task context just to
   remember it). Still forbidden in that module, as everywhere in `src/`: `.cursor()`,
   `ensure_connection`, `connect`, `django.db.transaction`, and any other use of a sync
   connection. `compile.scope` calls the module, through the single context manager
   `swapped(alias, wrapper)` that the module exposes (it yields nothing, so the previous wrapper
   is never handed out by any name the guard lets other code use); the guard lets only
   `compile/scope.py` import it, and also rejects dynamic imports (`importlib`, `builtins`,
   `__import__`). This narrows the issue's "`compile` module"
   wording to the Django boundary module and to these operations. The guard implementation is
   done in #3, not in this ADR.

   **Threat model of the guards (A101-A104).** They stop the code a contributor can write by
   accident: ordinary imports, attribute access, `getattr` with a constant name, and every route
   through Django or `asyncopation` *public* names (re-exports such as
   `django.db.models.base.connections`, `ConnectionHandler`, `psycopg_any`, `Database`,
   `BaseWrapper` aliases). They do not stop deliberate evasion: introspection and dunder walks
   (`__bases__`, `__mro__`, `__subclasses__`, `__loader__`, `__spec__`, `__dict__` / `vars()` of a
   module), `inspect`, `sys.modules`, strings assembled at run time, calling a function through a
   variable (`e = eval`), `gc`, `zipimport`. Those are known limits (listed in the `archlint`
   docstring, which has the full list; star imports are ruff F403) that architecture review
   covers, as are `BaseWrapper` handed on through `getattr(<asyncopation module>, "BaseWrapper")`,
   a call argument, `return` / `yield` or a lambda body inside `compile/` / `_django/`, and a
   class built with `type(...)`. The guard itself requires a class based on `BaseWrapper` to list
   `CompileOnlyMixin` before it and rejects calling `BaseWrapper(...)`, and a unit test checks the
   MRO of every Asyncopation subclass at run time. Also known: psycopg objects that an
   `asyncopation.drivers` module re-exports under a public name
   (`from asyncopation.drivers.postgresql import sql`): ADR-0003 forbids that as a convention
   that review enforces, not the guards.
7. **Amendments applied with this acceptance:** AGENTS.md non-negotiable 2, `architecture.md`
   invariant 2 and `.agents/rules/architecture.md` / `async-correctness.md` gain the
   `compile_scope` exception (the synchronous swap in `_django.connections`; no `await` inside it);
   ADR-0004's "never in a contextvar" is qualified: the swap uses asgiref's contextvar-backed
   storage only transiently and carries no state across an `await`.

## Spike results
Method. **The sweep installed the compile-only wrapper permanently** as `connections["default"]` so that every reachable read is recorded (a superset of what a scope covers; which of them a scope must enclose is the contract in Decision item 2). One-off scripts, not committed; the same check is owned from now on by the "zero sync
connections" assertion of the differential tests, #3). Django 6.1.3, PostgreSQL 17, MySQL 8.4,
MariaDB 11.8. Compile-only wrappers raised on `connect` / `ensure_connection` / `_cursor` and had
server info injected. Instrumented: `ConnectionHandler.__getitem__`, `Query.get_compiler`,
`SQLCompiler.__init__`, `as_sql` / `pre_sql_setup` / `execute_sql`, and the wrapper's connect
methods. Inputs: 120 derandomized Hypothesis QuerySets from `tests/support/strategies.py` x
`list / count / first / get / exists`; the ADR cases (`qs[:3].count()`, `distinct().count()`,
`annotate().count()`, `aggregate()`, `union().count()` ...); 19 write cases (related-table and
multi-table-inheritance `update`, `bulk_create` / `bulk_update`, `delete`, `save`, `update_or_create`,
`m2m add`). About 4.9k recorded events per backend; results are identical across backends except where
noted. Static survey of the installed source (every `connections[...]` read, `get_compiler(using)`
call and I/O reachable from `as_sql`) backs the runtime data.

### Reachability by stage

**generate** = inside `as_sql()` / `pre_sql_setup()`; **orchestrate** = Django evaluation methods
outside `as_sql()` (build the compiler, then execute); **execute** = cursor use.
Distinct source locations hit: 2 build, 5 generate, 17 orchestrate, 1 execute (3 compiler variants).

Port boundary for `acount()`: `QuerySet.count()` -> `Query.get_count` -> `get_aggregation` builds
the outer query, calls `compiler.execute_sql(SINGLE)` and converts the row in one function, so

reused unchanged.

### Is `connections` thread-scoped? (hypothesis check - partly refuted)
- `ConnectionHandler.thread_critical = True`, but asgiref's thread-critical `Local` is
  **thread-local only in sync code**. Inside a running event loop it is backed by a contextvar
  (`asgiref/local.py`, `_ThreadCriticalLocal._get_storage`): the storage is per async call stack
  (copy-on-write; visible to awaited code and tasks created afterwards, not to siblings or the
  parent), still never visible to other threads.
- uvicorn probe (ASGI app on the loop thread): loop task, `asyncio.gather` children share one
  wrapper; `sync_to_async(thread_sensitive=True)` threads, `sync_to_async(thread_sensitive=False)`
  / `asyncio.to_thread` threads each have their own; a swap on the loop thread is invisible to them.
- pytest-asyncio (session loop) runs on the same main thread as pytest-django's DB setup, but a
  coroutine sees a **different** wrapper object than the sync fixture (`connections["default"]` in the
  loop is not the setup object); the sync oracle called through `sync_to_async` uses a third one.
  A scoped swap on the loop thread coexisted with sync oracle and core async calls; a swap in a child
  task was invisible to the parent and siblings. Teardown showed the usual "database is being
  accessed by other users" when a test left an in-loop real connection open (not related to the swap).
- Consequence: the "install it as the loop thread's `connections[alias]`" wording of option A is
  wrong; installation is per async context. A permanent install would (a) not reach other tasks
  and (b) shadow the real wrapper for sync-oracle code run in the same context. The scoped swap
  (decision item 1) avoids both. Its cost is not free: each swap and restore on asgiref's `Local` runs `get_running_loop`, copies the alias dict and allocates a storage object; a `bench-micro` case measures it (#3).

### MySQL without mysqlclient
- Composed wrapper (`mysql.features` + `mysql.operations` + `mysql.compiler` + ported attributes
  `_data_types`, `operators`, `pattern_esc`, `pattern_ops`, `isolation_levels`, `data_types`,
  `display_name`, `data_type_check_constraints`, `mysql_server_data` / `_info` / `_version` /
  `_is_mariadb`, `sql_mode`, `get_database_version`) never imported `MySQLdb` (asserted after each
  run). Importing `mysql.features`, `operations` and `compiler` does not import it; `mysql.base` and
  `mysql.introspection` do.
- SQL and params identical, compared with Django's own wrapper (server data injected into both):
  770 statements per backend (150 Hypothesis QuerySets x 5 evaluators plus 20 named reads / writes /
  `select_for_update` / JSON / regex / date lookups), **0 mismatches** on MySQL 8.4 and MariaDB 11.8;
  187 `features` / `ops` / wrapper attributes equal (only object identity and set ordering differ).
  Caveat: the real-wrapper side used PyMySQL installed as `MySQLdb` because mysqlclient's native
  libraries are not installed here; SQL generation does not depend on the client library.
- Finding that changes the sub-decision: Django loads the `default` backend while defining models, so
  with a stock `ENGINE` mysqlclient is required by Django whatever Asyncopation does. Without
  mysqlclient only works when `ENGINE` points at a module providing the compile-only wrapper
  (verified: `django.setup()` and the whole sweep ran with such an engine and no `MySQLdb`).
- PostgreSQL has no such split: `django.db.backends.postgresql.*` imports psycopg at import time, so
  `_django.postgresql` pulls psycopg in through Django (drivers remain the only direct importers).

### Deviations from the working hypothesis
1. `connections` is per async context inside a loop, not per loop thread (above).
2. `select_for_update` compilation connects (`get_autocommit`); not in the ADR's original list.
3. `pre_sql_setup` I/O is not MySQL-only: PostgreSQL / MariaDB hit it for multi-table inheritance.
4. Dropping mysqlclient from a project is only reachable through an Asyncopation `ENGINE`, not by the wrapper alone; that option is not adopted (Decision 5).

## Consequences
Unblocks Phase 1 `acount` / aggregate paths and the write compilers. Follow-ups: #3 adds the A102
exception for `asyncopation._django.connections` (operations listed in Decision 6),
`compile_scope`, server-info injection and the "zero sync connections" assertion; #6 ports
`get_aggregation` / `has_results` and the MySQL composed wrapper with its drift test; Phase 5 ports
`pre_sql_setup` as a core. ADR-0002 and ADR-0004 refer to this ADR for how compilers reach the
wrapper and whether Django's own wrappers receive server info (they do not).

On MySQL / MariaDB with the stock `ENGINE`, Django still requires mysqlclient at startup, so
users run two connection pools (Django's sync one and Asyncopation's asyncmy pool); documentation
for that is tracked in the Phase 6 issue "Docs: MySQL setup notes".

## Validation
- spike: list of every `connections[...]` / `get_compiler(using)` path hit by the differential
  suite, with the chosen handling for each.
- differential: `acount()` on `qs[:3]`, `distinct()`, `annotate()` passes with zero sync connects.
- drift tests: ported MySQL wrapper attributes equal Django's; SQL and params identical to Django's
  wrapper on the differential suite (the spike's 770-statement sweep); ledger symbols exist; asgiref
  per-context `Local` semantics pinned (swap invisible to siblings, parent and executor threads).
- unit (`compile_scope`): restores when the previous wrapper was present, absent, on exception and
  nested; no sync connect inside; wrapper `connect` / `ensure_connection` / `_cursor` raise;
  `get_autocommit` answers from the scope argument.
- concurrency: `asyncio.gather` with one task in `async_atomic` doing a `select_for_update` compile
  and one outside; cancellation around compile.
- differential, zero sync connections: `acount()` on `qs[:3]`, `distinct()`, `annotate()`,
  `union()`; `aexists()`; materialization after the scope has exited.
- Phase 5: `pre_sql_setup` core against MySQL related / multi-table updates; `bulk_create`,
  `bulk_update` prepare phases inside a scope.
